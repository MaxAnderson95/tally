# Account identity and preferences

The shared owner reconciles complete subscription inventory before scheduling collection. `OpenCodeInventory.swift` reads only the credential columns it needs; activity tables do not participate in credential compatibility checks. Supported authentication is Anthropic `claude-subscription`, OpenAI `chatgpt-browser`/`chatgpt-headless`, xAI `device`/legacy `browser`, and OpenCode Go keys. Unsupported methods and integrations are excluded before deduplication. OAuth credentials remain included when expired; Tally does not refresh them or infer that expiry requires reauthentication.

`AccountIdentity.swift` keeps per-database namespaces, opaque Account IDs, pins, six-color sequence counters, producing-identity evidence, and current last-good readings in `~/Library/Application Support/Tally/accounts.json`, outside the app bundle. Preference setters save immediately, without waiting for Quit. Writes use atomic file replacement with owner-only permissions; failure remains visible in native settings and does not stop collection. A file lock and comparison with the last loaded/saved bytes prevent a second app owner or `--collect-once` from overwriting newer settings. Explicit preference changes report failure and roll back in memory when saving fails. An unreadable/damaged file remains untouched, and saving stays blocked until the user restores the file and restarts Tally. A missing file starts fresh. Command recovery uses separate required storage and never treats missing identity state as permission to consume.

## Continuity rules

- Database file identity hashes the volume UUID, file number, and file creation time. The volume UUID survives macOS filesystem-device renumbering at reboot. Each namespace retains this hash in the optional `databaseFileIdentity` field. Migration binds the newest matching legacy device-based namespace to that hash while keeping its namespace key, Account IDs, preferences, cached readings, and command-history associations. For a first upgrade after a reboot, Tally recomputes legacy hashes with the current device major and Darwin's generated 16-bit filesystem-device minors, retaining the exact inode and creation time; it never selects a namespace just because its credential rows match. An older namespace matching a recycled current device number cannot override a newer matching namespace. Paths, credential row IDs, labels, active selection, and activity schema are not namespace identity. Symlinks/renames recognize the same file; replacement by a different file creates a namespace even with identical rows. A destructive rewrite that preserves all filesystem identity attributes cannot be distinguished from changes to that same database using these attributes alone.
- OpenAI `metadata.accountID` is the verified workspace selector. Equal known selectors prove the same service target even across token refresh. Different selectors remain distinct with a shared token. Known versus missing selector is uncertain and never deduplicates.
- Go key equality proves continuity. Distinct Go keys remain separate. For Anthropic/xAI and OpenAI without a known selector, an unchanged access or refresh token proves continuity. Fully rotated tokens without stable provider evidence create a new Account with no inherited readings. Saved preferences can still follow the same credential row. Tally does not infer producing identity from unverified JWT claims, email, names, or row IDs.
- Proven duplicates choose creation time then credential ID. Initial assignment sorts by provider, lowercased name, original name, then stored credential ID. IDs are random opaque UUIDs persisted with the association. Later display ties use opaque Account ID; pins retain their saved order.
- Successful removal clears readings/pins, retaining identity/color association. A recognized return keeps its ID/color and starts unpinned. Failed inventory reads keep last-known inventory and stale groups. Database switching cancels old collection and prevents its completion from updating the new namespace. Returning restores readings stale.

Anthropic and xAI Accounts do not preserve their ID or readings across a refresh that rotates both tokens. Colors and pin/order preferences follow the stable OpenCode credential row. Warm-up settings follow that row and workspace, including suspended attempts and cooldowns, so token rotation cannot replay a message or move it to a different OpenAI workspace.

Icon colors are cosmetic preferences keyed by a hash of the provider and OpenCode credential row ID within each database namespace. They survive token rotation and app restarts independently of Account identity, readings, and reset commands. Existing saved colors seed these preferences when their credentials are next recognized. Changing the color saves immediately and rolls back on a write failure. A different credential row or database namespace has its own color preference.

Pinned and unpinned ordering use the same stable credential-row keys within each database namespace. Native and web Settings move Accounts within their pinned or unpinned list. Pinned Accounts remain first. Saved unpinned Accounts precede newly discovered Accounts, which use the default provider/name ordering until rearranged. Pinning temporarily removes an Account from the unpinned list; unpinning restores its saved position when available. Token rotation preserves both orders without transferring readings. Failed saves retain the previous order.

`TallyOwner.identityEvidence(accountID:)` gives later command recovery a Codable, nonsecret target comparison. `same` proves a match across namespaces; `different` requires a different provider or different known OpenAI workspace; `uncertain` must not release an unresolved command block. The command layer must retain original namespace/Account/operation identities and evidence durably, refresh inventory before targeting, and refuse uncertainty until resolved by its command policy. REST never includes this evidence. Reading or acknowledging an old command must not depend on the Account still being in inventory.

The activity layer (#21) must use the owner's current inventory namespace, clear its displayed view on namespace departure, and validate activity-specific schema separately. The provider collectors (#17-19) must keep using selected stored credentials rather than active connections. The presentation layer (#20) consumes persisted `pinned`, `pinOrder`, and `identityColorIndex`; the complete logo/pin renderer and exact visual palette remain in that layer.

## App lifecycle

Native and web Settings call the same owner's preference setters. Colors, pinned/unpinned ordering, and warm-up configuration and recovery state are saved in `accounts.json`. Database path, listener port, allowed web origin, and login-setup state use the macOS preferences domain `net.maxanderson.tally`; macOS owns the actual launch-at-login registration. Normal app updates and reinstalls replace the app bundle while retaining both locations. Deleting the data directory or preferences explicitly removes the saved settings. A genuinely different OpenCode database has independent settings; Tally does not copy warm-up or reset-command targets into it.
