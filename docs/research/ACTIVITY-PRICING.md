# API-equivalent pricing for retained OpenCode activity

Research for issue 11. Primary documents and public metadata retrieved September 7, 2026. This asset supplies evidence and a recommendation for Max's presentation decision in issue 7; it does not accept a product policy or implement Tally.

https://github.com/MaxAnderson95/tally/issues/11

https://github.com/MaxAnderson95/tally/issues/7

## Recommendation

Bundle a small, reviewed, versioned price table derived from the four providers' first-party price documents. Match the recorded provider and model ID exactly, with individually documented aliases only. Use models.dev as a discovery and cross-check source, not the pricing authority. Its live catalog now contains six of the seven entries missing from issue 10's bundled snapshot, but availability does not establish correct or complete prices: GLM-5.3-Flash has different rates in the catalog and Go's first-party table, DeepSeek's time tiers are missing, and Anthropic's two cache-write prices collapse to one. [C1-C4, G1, A1]

The minimum sufficient valuation policy is **current standard API-equivalent token cost at the bundled revision**, in USD per million recorded tokens. For Go, use Go's own published per-token reference table, with the Go provider label qualification from issue 10. This is a comparison value, not a subscription charge, historical bill, quota debit, or claim about the actual dispatched endpoint. Exclude Zen-labeled activity before matching. Do not multiply Go prices by subscription allowances or quota multipliers. [G1, S4]

Keep three pricing outcomes: a fully priced recorded-token subtotal, a bounded estimate where documented alternatives explain the uncertainty, and unpriced activity where they do not. Anthropic cache writes usually require a range because the retained record loses the 5-minute/1-hour split. Unknown model IDs remain unpriced. If the presentation cannot show ranges, show those rows as partially priced with their known component subtotal, not a guessed single total. Missing usage remains a separate token-coverage gap.

This supports estimates across all four providers while explicitly limiting coverage. It does **not** support a complete scalar estimate for all retained activity. Max must accept the standard-rate comparison, range/partial presentation, and qualified Go provider scope before the presentation/spec decision is complete.

### Concrete reasons not to import catalog prices blindly

1. **GLM-5.3-Flash:** models.dev says input/output/cache read `0.075/0.25/0.015`, and names the Go entry `GLM-5.3-Flash (2x usage)`. The first-party Go document says `0.15/0.50/0.03`. The catalog label is evidence of a usage-oriented adjustment, but it does not establish the current server billing mechanism or effective dates. For the recommended published-reference comparison use Go's documented table and record the discrepancy; do not average the rates or apply another multiplier. [C2, G1]
2. **DeepSeek V4 Flash:** catalog base rates are `0.22/0.66/0.007`. Go publishes those off-peak rates and peak rates `0.44/1.32/0.014`. A catalog-only estimate understates a peak-rate valuation by half. [G1]
3. **Anthropic cache writes:** catalog `cache_write` is the 5m rate. Fable 5.1's first-party price is $12.50/MTok for 5m and $20/MTok for 1h. There is no retained duration split to justify selecting $12.50 for every write. [A1, S1-S2]
4. **Threshold encoding:** catalog `tiers[].tier.size` does not by itself settle an inclusive/exclusive comparison. OpenCode's runtime uses `context > size`. xAI's Grok 4.6 model/pricing tables use `>= 200,000`; its generic cache guide says “exceed.” Go's Grok table uses `> 200K`. Preserve provider-specific evidence and flag equality instead of sharing one unchecked comparison across providers. [X1-X3, G1, S1]
5. **Misleading compatibility field:** the public OpenAI catalog includes `context_over_200k` for models whose actual threshold is 272,000, alongside the explicit `tiers` entry. Use the documented threshold, not that legacy field name. [O1-O4, C3]
6. **Zero is not proof:** Ox Alpha's catalog explicitly records zero and deprecated status, but that supplies neither a current public API equivalent nor first-party historical effective dates. A missing component is different from an explicit zero, and an entry's existence is different from a verified price. [C4]

All rates in the following tables are USD per **1,000,000 tokens**, without taxes, negotiated discounts, subscription fees or server-tool fees. `I` means noncached input; `O+R` means recorded non-reasoning output plus recorded reasoning; `CR` means cache read; `CW` means cache write. A dash means no separate price established by the cited table, never an instruction to substitute zero.

These tables cover every provider/model pair observed in the checked recent 30-day window. They are research inputs for a candidate bundle, not an exhaustive historical catalog.

## Component semantics and missing metadata

The current V2 normalization yields non-overlapping `I`, `O`, `R`, `CR`, `CW`; their sum is OpenCode's recorded token total. The stored `O` is already output minus reasoning, so add `O + R` once at the output rate. Do not subtract `CR` from `I` again. Protocol-level output counts can include non-visible work; “visible output” is OpenCode's field interpretation, not a count audited from rendered text. [S1-S2]

```text
prompt = I + CR + CW
knownUSD = (I * pI + (O + R) * pO + CR * pCR) / 1,000,000
fullUSD = knownUSD + CW * pCW / 1,000,000
```

The second formula applies only when the write rate and applicable tier are established. If `CW` is positive and `pCW` is unavailable, the first formula is a **known-component subtotal**, not a complete price. A zero recorded component contributes zero by arithmetic without asserting that its unknown unit price is zero. Missing entire usage does not satisfy that condition.

| Retained fact or missing fact | Pricing consequence |
|---|---|
| Provider/model/optional variant | Exact-pair matching is possible; current configuration cannot prove old aliases or routes |
| Five normalized token components | Standard token comparison possible for verified rates; older imported/migrated normalization was not re-audited |
| Missing provider values normalized to zero upstream | Cannot distinguish omitted component from explicitly reported zero; all coverage is relative to recorded tokens |
| One combined cache-write count | Anthropic 5m/1h split unavailable; range or partial amount |
| No frozen price revision/effective tariff | Historical billed amount cannot be reconstructed from current prices |
| No actual credential, route, geography or authentication method | No Account attribution, historical subscription-vs-API proof, regional price selection or billing reconciliation |
| Optional generic provider state | A field named `serviceTier` exists in observed records, but is not a complete cross-provider historical pricing contract; values were not read in this research |
| No raw usage metadata on retained assistants | Lost iteration details, TTL splits, modality subcounts and tool billing units cannot be reconstructed by importing a better catalog |
| Creation and completion times | Calendar bucketing works under issue 10's policy; exact server-side time-tier selection remains unproven |
| Internal title/compaction requests outside the model-attributed assistant projection | Do not allocate their costs to the session's latest model |

The protocol source has an in-memory raw usage metadata object and, for Anthropic iterations, separate effective context information. The retained assistant schema does not persist those fields. A future source could therefore need more than `I+CR+CW` for a model billed by per-iteration context or modality. Do not generalize the current one-request OpenAI/xAI tier examples to all possible providers or request modes. [S2-S3]

## Coverage and aggregate contract proposed for issue 7

For each provider/model/day and the cross-provider view, retain the same filtered records and show:

- Recorded token components and total, plus rows with missing usage. Unknown token quantities cannot be added into an “unpriced token” count as zero.
- Exact model-match coverage separately from pricing coverage. Distinguish matched-and-fully-priced recorded rows, bounded/partially-priced rows, unpriced model/tier/component rows, and missing usage.
- A sum of fully priced rows, with its priced row/token denominator. If known components from partial rows are included in a different subtotal, name that component scope explicitly.
- Any bounded amount separately, with the reason for its bounds. If unknown models or components have no finite verified bound, the whole-provider amount has no complete upper bound; adding known bounds does not make it complete.
- Unpriced model names, recorded token amounts and reason codes such as unknown model, missing rate, missing write duration, ambiguous threshold, unresolved time tier, or unreviewed historical model.
- Price revision, source observation date, standard-rate comparison basis, and the separate partial local-record coverage from issue 10.

Do not mix OpenCode-recorded cost into a recomputed estimate to fill gaps. Do not infer that a stored zero is free, infer USD/MTok from a recorded ratio, average provider cost/token ratios, or divide a partial cost sum by all recorded tokens and call it the effective price. A cost/MTok comparison is valid only for the same priced subset and a stated token definition.

If the user selects a range containing no retained activity, show “no recorded activity.” If rows exist but no rates match, show tokens plus “unpriced,” not `$0`. If all recorded components are zero and the model is unverified, preserve the unverified status even though arithmetic over the zero quantities is zero. A complete estimate of recorded tokens still remains a partial account of real requests because of deletions, missing final usage, imports and omitted overhead.

## Revision and update proposal

The smallest sufficient v1 source is a **bundled reviewed table**, not a runtime pricing service or a new dependency. Treat `2026-09-07` as an observation date for the candidate evidence, not a provider-wide price effective date or an already released bundle identifier.

Each admitted entry should preserve the exact recorded provider/model key; pricing reference provider/model; exact or explicit-alias evidence; USD and per-million units; rates with unknown components represented as unknown; context/time conditions including comparison operators; documented alternative write durations; standard comparison assumptions; primary URLs; retrieval date; and any immutable source SHA. Record a known effective interval only when the provider actually supplies it. Model release date, catalog `last_updated`, HTTP observation time and model-list `created` are not interchangeable with tariff effective dates.

Bundle the reviewed rates, compact source excerpts and a source manifest together. Assign an immutable revision/content digest in the future implementation and retain it in derived cached views. The first-party Go document is already available at a Git SHA. Other live documentation did not supply a verified immutable revision in this investigation: archive the relevant public extracts alongside the normalized rates at release time. Hashing a live response identifies those bytes, but a hash alone does not make them publicly retrievable later.

Update with an ordinary reviewed app release: retrieve primary sources, compare exact model IDs and component/tier changes, investigate discrepancies, verify synthetic fixtures and unknown cases, then replace the bundled revision. Do not silently fetch models.dev at runtime and reprice old cached amounts. A successful recomputation can revalue the chosen retained window at the new current revision; label that revision change, since the same historical token counts can now have a different comparison value. An old cached view remains tied to its old revision until recomputed.

Historical effective pricing is a different feature. The retained DB does not contain a tariff revision, and a current catalog Git history cannot establish what price the provider actually applied at request time. No complete historical tariff archive was established here. Retired IDs, changing aliases, promotions and custom routing remain historical unknowns. Keep OpenCode-recorded cost as a separate observed field with issue 10's provenance warning.

```sql
SELECT json_extract(m.data,'$.model.providerID') AS provider,
 json_extract(m.data,'$.model.id') AS model,
 count(*) AS rows, count(json_extract(m.data,'$.tokens')) AS token_rows,
 sum(json_extract(m.data,'$.tokens.input')
   + json_extract(m.data,'$.tokens.output')
   + json_extract(m.data,'$.tokens.reasoning')
   + json_extract(m.data,'$.tokens.cache.read')
   + json_extract(m.data,'$.tokens.cache.write')) AS tokens
FROM session_message m JOIN session_v2 s ON s.id=m.session_id
WHERE m.type='assistant'
 AND (s.fork_session_id IS NULL OR m.time_created>=s.time_created)
 AND date(m.time_created/1000,'unixepoch','localtime')>=date('now','localtime','-29 days')
 AND m.time_created<=unixepoch('now')*1000
 AND json_extract(m.data,'$.model.providerID') IN ('anthropic','openai','opencode-go','xai')
GROUP BY 1,2 ORDER BY 1,2;
```
